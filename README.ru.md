# fetch-layer

[English](./README.md) | **Русский**

HTTP-клиент, который собирается из слоёв. Каждый слой решает одну задачу: авторизация, повторы, идемпотентность. Слои подключаются по мере надобности, порядок их вызова проверяется при создании клиента.

Три встроенных слоя и единый `ApiError`:

- `withAuth` - обновление токена при 401 с одним refresh на все параллельные запросы, circuit breaker при недоступном refresh;
- `withRetry` - повторы 5xx и сетевых ошибок с учётом `Retry-After`;
- `withIdempotency` - один `Idempotency-Key` на всю операцию, включая повторы;
- `ApiError` - единый формат ошибок с готовыми `code`, `fields`, `requestId`.

Ноль зависимостей, tree-shaking.

## Кому подойдёт

- **SPA с авторизацией.** Пять параллельных запросов получают 401 одновременно. Без single-flight каждый пойдёт за новым токеном, часть запросов уйдёт с устаревшим и снова получит 401. `withAuth` запускает один refresh на все ожидающие запросы.

- **API с мутирующими операциями.** Заказы, платежи, бронирования. Хочется повторять 5xx и таймауты, но POST с созданием заказа создаст два заказа. `withIdempotency` генерирует ключ один раз и сохраняет его до подтверждения сервером.

- **Несколько API в одном приложении.** Публичный и приватный, разные токены, разные форматы ошибок. Каждый API - отдельный клиент со своими слоями и своим `SessionProvider`.

## Какие проблемы решает

### Сессия истекла, запросы падают с 401

Пять запросов уходят одновременно, все получают 401. Без координации каждый запустит свой refresh. Получится пять параллельных запросов за новым токеном, гонка записи в хранилище, актуальным останется только один. Часть исходных запросов уйдёт с уже невалидным токеном и снова получит 401.

`withAuth` собирает все ожидающие запросы в один refresh. Пока он выполняется, остальные ждут. Когда токен обновится, каждый повторяется с новым заголовком. Один refresh на все запросы вместо пяти.

### Повторы и дубликаты

Сетевые ошибки и 5xx: сервер может быть недоступен, соединение может оборваться. Повтор часто проходит со второй или третьей попытки.

Повтор создаёт дубликаты, если операция не идемпотентна. POST на создание заказа при повторе создаст два заказа: первый мог дойти до сервера, ответ потерялся, повтор создал ещё один.

Решение - `Idempotency-Key`. Сервер по нему распознаёт дубликат и возвращает результат первой операции. Проблема в том, что ключ должен быть один на всю логическую операцию, включая все повторы и refresh между ними.

`withIdempotency` генерирует ключ один раз, до первой попытки, и сохраняет его до подтверждения сервером. Даже если запрос упал по сети и повторяется через пять минут из другого места - ключ тот же.

### Разные форматы ошибок

У каждого бэкенда свой формат ошибок. Один отдаёт `{ code, message }`, другой `{ error: { code } }`, третий RFC 7807. Разбор повторяется в каждом месте, где обрабатывается ошибка, и в итоге размазан по всему приложению.

Библиотека приводит все ошибки к `ApiError`. Поля одинаковые независимо от того, что вернул сервер: `code`, `message`, `fields`, `requestId`, `isRetryable`, `isCancelled`.

### Обновление токена временно недоступно

При обновлении токена сервер может быть недоступен: сеть упала, refresh-эндпоинт вернул 5xx. Без защиты каждый новый 401 будет запускать новую попытку refresh, добавляя нагрузку на сервер.

`withAuth` временно блокирует refresh после сбоя. Пока блокировка активна, 401 возвращается приложению без попытки обновления. `onCircuitOpen` и `onCircuitClose` сообщают о переходе состояния.

## Возможности

- **Авторизация.** `withAuth` работает с любым `SessionProvider` - три метода: `getAuthHeaders`, `refresh`, `clear`. Три состояния refresh (`success`, `definitely-failed`, `temporarily-failed`) дают приложению контроль: разлогинить пользователя или повторить позже. Circuit breaker с настраиваемым `circuitBreakerMs` и `refreshTimeoutMs`. `resetRefreshCircuit` для ручного сброса.

- **Идемпотентность.** `withIdempotency` хранит ключ в `sessionStorage`, `localStorage` или памяти. Для кастомного хранилища - интерфейс `IdempotencySource` из двух методов и утилита `stableSerialize` для отпечатка тела. `maxEntries` ограничивает размер хранилища, вытеснение - по времени использования.

- **Повторы запросов.** `withRetry` настраивается: `maxAttempts`, `baseDelayMs`, `maxDelayMs`, `jitterRatio`, `retryOnNetwork`, `retryOnTimeout`. Свои политики через `shouldRetry`, `computeDelay`, `onBeforeRetry`. `Retry-After` от сервера имеет приоритет над вычисленной задержкой.

- **Ошибки.** Единый `ApiError` с геттерами `isRetryable`, `isCancelled`, `isAuthError`, `isUncertain` и другими. `err.fields` - готовая структура `Record<string, string>` для формы. Три встроенных парсера в `fetch-layer/error-body` для `content`, `error`, RFC 7807. Свой парсер через `parseErrorBody`.

- **Транспорт.** Валидация `baseUrl`, `timeoutMs`, `fetch` и порядка слоёв при создании клиента. Заголовки принимаются как `Record`, `Headers` или массив пар. `defaultHeaders` для сквозных заголовков. Per-request `timeoutMs` и `signal`. `requestWithMeta` для HTTP-метаданных. `fetchOptions` для остальных параметров `fetch`.

- **Тела запросов.** JSON, `FormData`, `Blob`, `File`, `ArrayBuffer`, `TypedArray`, `DataView`, `URLSearchParams`, `ReadableStream`, Node.js `stream.Readable`. Работа с типами из iframe и Worker. Рекурсивная проверка: вложенные несериализуемые значения отклоняются до отправки с `BODY_SERIALIZATION_ERROR`.

- **Слои.** Свой слой - объект из четырёх полей: `name`, `stage`, `wrap`, `attach`. `LayerContext` даёт доступ к `warn`. Приоритеты `2.5` и `1.5` для вставки между встроенными.

## Установка и первый запрос

```
npm install fetch-layer
```

```ts
import { createClient } from 'fetch-layer';

const client = createClient({ baseUrl: '/api' });

const products = await client.get<Product[]>('/products');

const review = await client.post('/reviews', {
  productId: products[0].id,
  rating: 5,
  comment: 'Отличный товар',
});
```

Метод `get` возвращает распарсенное тело. `post` отправляет объект как JSON и возвращает ответ сервера. Все ошибки приводятся к `ApiError` - ловите их через `try/catch` или `.catch()`.

### Подключение слоёв

Слои передаются в `layers`. Порядок в массиве - от самого внешнего к самому внутреннему:

```ts
import { createClient } from 'fetch-layer';
import { withAuth, withRetry, withIdempotency, sessionStorageSource } from 'fetch-layer/layers';

const client = createClient({
  baseUrl: '/api',
  layers: [
    withIdempotency({ source: sessionStorageSource() }),
    withRetry({ maxAttempts: 3 }),
    withAuth({ provider: sessionProvider }),
  ],
});
```

Что здесь происходит:

- `withIdempotency` оборачивает всё остальное. Ключ генерируется один раз на операцию и не меняется при повторах.
- `withRetry` повторяет запрос при 5xx, сети и таймаутах, но не трогает ключ.
- `withAuth` добавляет заголовки авторизации и обновляет токен при 401.

Порядок нельзя переставить произвольно: библиотека проверяет его при создании клиента. Если поменять `withIdempotency` и `withRetry` местами, ключ будет генерироваться заново на каждом повторе - это ошибка. `createClient` выбросит исключение с указанием, какой слой нарушил правило.

Если слои не нужны, `createClient({ baseUrl: "/api" })` даёт чистый HTTP-клиент без авторизации, повторов и идемпотентности.

## Требования

Библиотека работает на Node.js 20.6+, в современных браузерах, Deno и Bun.

Нужен глобальный `fetch`. Если его нет, `createClient` выбросит исключение.

Пакет только ESM. CommonJS не поддерживается.

`crypto.randomUUID` нужен только если подключён `withIdempotency` со встроенным генератором ключей. Проверяется при первом мутирующем запросе.

## Модули

Библиотека разбита на модули. Размер бандла зависит от того, что импортируете.

| Модуль                    | Что экспортирует                                                                                          |
| ------------------------- | --------------------------------------------------------------------------------------------------------- |
| `fetch-layer`             | `createClient`, `ApiError`, `toApiError`, хранилища и публичные типы                                      |
| `fetch-layer/layers`      | Фабрики всех встроенных слоёв и источники ключей идемпотентности                                          |
| `fetch-layer/auth`        | Типы `SessionProvider`, `RefreshResult`, `SessionExpiredReason`, `resetRefreshCircuit`                    |
| `fetch-layer/idempotency` | `IdempotencySource`, `IdempotencyContext`, `IdempotencyOutcome`, `createSessionSource`, `stableSerialize` |
| `fetch-layer/retry`       | Только `withRetry` и его опции                                                                            |
| `fetch-layer/storage`     | `StorageLike`, `createMemoryStorage`, `fromWebStorage`                                                    |
| `fetch-layer/error-body`  | Парсеры `errorBodyParsers` и типы `ErrorBodyParser`, `ParsedErrorBody`                                    |

### Прямые импорты для минимального размера

`fetch-layer/layers` реэкспортирует все три слоя. Если используете только один, импортируйте его напрямую: бандлер не потянет остальные.

```ts
import { withRetry } from 'fetch-layer/retry';
import { withAuth } from 'fetch-layer/auth';
import { withIdempotency, sessionStorageSource } from 'fetch-layer/idempotency';
```

`fetch-layer/layers` остаётся удобным вариантом для типового случая: один импорт вместо трёх.

## Как устроены слои

Каждый слой - обёртка вокруг функции запроса. Метод `wrap` получает `next` и возвращает свою версию. Это паттерн Decorator (GoF): добавляет поведение, сохраняя интерфейс. Первый слой в массиве видит запрос раньше всех, последний - позже всех. Встроенные слои идут в порядке: идемпотентность, повторы, авторизация, отправка.

У каждого слоя есть приоритет (stage). Чем больше число, тем раньше слой получает запрос. Встроенные приоритеты: `withIdempotency: 3`, `withRetry: 2`, `withAuth: 1`. Если нужен свой слой между встроенными, используйте дробные значения: `2.5` встанет между идемпотентностью и повторами, `1.5` - между повторами и авторизацией.

Слои без stage в проверке не участвуют. Их можно ставить в любое место массива.

Порядок вызова не произвольный. Ключ идемпотентности должен сгенерироваться до первой попытки, иначе каждый повтор создаст новый ключ и дедупликация сломается. Авторизация должна стоять после повторов, чтобы 401 попал в auth-слой, а не в retry. `createClient` проверяет порядок и выбрасывает исключение, если он нарушен: в сообщении будет имя слоя, который встал не туда.

Каждый клиент имеет собственный экземпляр состояния. Один и тот же объект `Layer` можно передать в два `createClient`: у каждого будет свой `RefreshManager`, свой набор предупреждений, свой счётчик. Они не будут мешать друг другу.

### Почему слоистая архитектура вместо хуков и интерцепторов

Слой - это декоратор: он получает `next` и возвращает свою версию. Такой форме доступно то, чего не могут колбэки: не вызвать запрос, вызвать его дважды, поймать ошибку и продолжить.

Хук в ky и ofetch и интерцептор в axios - это колбэки, которые вызываются в фиксированной точке: до запроса или после ответа. Каждый получает данные и возвращает их же.

`withRetry` вызывает `next` в цикле, пока не получит успешный ответ. `withAuth` перехватывает 401, отдельно делает refresh, затем вызывает `next` с новым токеном. `withIdempotency` оборачивает вызов целиком и удаляет ключ только после подтверждения от сервера.

Хуки и интерцепторы умеют только данные до и после. Управлять вызовом - не умеют.

## Совместная работа с Tanstack Query

fetch-layer встраивается в `queryFn` и `mutationFn`.

```tsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

const client = createClient({
  baseUrl: '/api',
  layers: [
    withIdempotency({ source: sessionStorageSource() }),
    withAuth({ provider: sessionProvider }),
  ],
});

function useUser(id: string) {
  return useQuery({
    queryKey: ['user', id],
    queryFn: ({ signal }) => client.get<User>(`/users/${id}`, { signal }),
  });
}

function useCreateOrder() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (order: Order) => client.post<Order>('/orders', order),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['orders'] });
    },
  });
}
```

`queryFn` получает `signal` от Tanstack Query, fetch-layer его принимает и объединяет с внутренним таймаутом. Отмена работает в обе стороны.

Основной конфликт - retry. У Tanstack Query есть свой retry для `useQuery`, у fetch-layer - свой для HTTP. Если оба включены, 3 попытки x 3 попытки = 9 запросов. Оставьте retry в одном месте:

```ts
// Retry в fetch-layer, Tanstack Query без retry.
const client = createClient({
  baseUrl: '/api',
  layers: [withRetry({ maxAttempts: 3 })],
});

useQuery({
  queryKey: ['user', id],
  queryFn: () => client.get<User>(`/users/${id}`),
  retry: false,
});
```

Остальное совместимо без адаптеров: `ApiError` пробрасывается в `error`, `signal` принимается как есть, Devtools показывает вызовы `queryFn` без изменений.

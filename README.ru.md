# fetch-layers

[English](./README.md) | **Русский**

HTTP-клиент, который собирается из слоёв. Каждый слой решает одну задачу: авторизация, повторы, идемпотентность. Слои добавляются по необходимости, порядок слоёв проверяется при создании клиента.

Три встроенных слоя:

- `withAuth` - обновление токена при 401, один refresh на все параллельные запросы;
- `withRetry` - повторы 5xx и сетевых ошибок с учётом `Retry-After`;
- `withIdempotency` - один `Idempotency-Key` на всю операцию, включая повторы.

Все ошибки слоёв и транспорта приводятся к классу `ApiError`. Ноль зависимостей, tree-shaking.

## Кому подойдёт

- **SPA с авторизацией.** Несколько запросов уходят одновременно и получают 401. `withAuth` запустит один refresh на все запросы и повторит каждый с новым токеном.

- **API с мутирующими операциями.** Заказы, платежи, бронирования. Требуется повторить запрос при 5xx и таймауте, но повтор POST на создание заказа создаст второй заказ. `withIdempotency` генерирует ключ один раз и сохраняет его до подтверждения сервером.

- **Несколько API в одном приложении.** Публичный и приватный, разные токены, разные форматы ошибок. Каждый API - отдельный клиент со своими слоями и своим `SessionProvider`.

## Какие проблемы решает

### Сессия истекла, запросы падают с 401

Пять запросов уходят одновременно, все получают 401. Без координации каждый запрос запустит свой refresh - пять обновлений вместо одного. Токен записывается в хранилище пять раз с гонкой: побеждает последний, а часть запросов остаётся со старым токеном и снова получает 401.

`withAuth` собирает все ожидающие запросы в один refresh. Пока он выполняется, остальные ждут. Когда токен обновится, каждый повторяется с новым заголовком. Один refresh на все запросы вместо пяти.

### Повторы и дубликаты

Сетевые ошибки и 5xx: сервер может быть недоступен, соединение может оборваться. Повтор часто проходит со второй или третьей попытки.

Повтор создаёт дубликаты, если операция не идемпотентна. POST на создание заказа при повторе создаст два заказа: первый мог дойти до сервера, ответ потерялся, повтор создал ещё один.

Решение - `Idempotency-Key`. Сервер по нему распознаёт дубликат и возвращает результат первой операции. Проблема в том, что ключ должен быть один на всю логическую операцию, включая все повторы и refresh между ними.

`withIdempotency` генерирует ключ один раз, до первой попытки, и сохраняет его до подтверждения сервером. Даже если запрос упал по сети и повторяется через пять минут из другого места - ключ тот же.

### Разные форматы ошибок

У каждого бэкенда свой формат ошибок. Один отдаёт `{ code, message }`, другой `{ error: { code } }`, третий RFC 7807. Без общего механизма разбор приходится повторять в каждом месте, где ошибка обрабатывается.

Библиотека делит поля ошибки на два слоя. Структурный слой одинаков для всех серверов: `kind`, `status`, `isRetryable`, `isCancelled`, `isUncertain`, `requestId` (из заголовка `X-Request-Id`), `retryAfterMs`. Контентный слой приходит из тела ответа: `code`, `message`, `fields`, `details`. По умолчанию клиент понимает плоский формат `{ code, message, fields }` и plain-text. Для остальных форматов (Fastify, RFC 7807, DRF, Laravel, `{ error: { code } }`) приложение передаёт свою функцию разбора через `parseErrorBody`.

Полное тело ответа всегда доступно в `err.rawBody`, даже если формат не распознан.

### Обновление токена временно недоступно

При обновлении токена сервер может быть недоступен: сеть упала, refresh-эндпоинт вернул 5xx. Без защиты каждый новый 401 запускает новую попытку refresh, и это добавляет нагрузку на сервер.

`withAuth` временно блокирует refresh после сбоя. Пока блокировка активна, 401 возвращается приложению без попытки обновления. `onCircuitOpen` и `onCircuitClose` сообщают, когда предохранитель открывается или закрывается.

## Возможности

- **Авторизация.** `withAuth` работает с любым `SessionProvider`. Чтобы подключить слой, реализуйте три метода: `getAuthHeaders`, `refresh`, `clear`. Три состояния refresh (`success`, `definitely-failed`, `temporarily-failed`) дают приложению контроль: разлогинить пользователя или повторить позже. Параметры предохранителя: `circuitBreakerMs` и `refreshTimeoutMs`. Предохранитель открывается только на сетевые ошибки, таймауты и 5xx, а не на ошибки в `refresh`. Функция `resetRefreshCircuit(client)` сбрасывает его вручную, если приложение знает, что проблема устранена.

- **Идемпотентность.** `withIdempotency` добавляет заголовок `Idempotency-Key` на все мутирующие методы (POST, PUT, PATCH, DELETE). Для эндпоинтов, которые заголовок не принимают, передайте `skipIdempotency: true` на конкретном запросе. Ключ можно хранить в `localStorage`, `sessionStorage` или памяти, в зависимости от того, требуется ли сохранять его при перезагрузке. Для кастомного хранилища - интерфейс `IdempotencySource` (два метода) и утилита `stableSerialize` для отпечатка тела. `maxEntries` ограничивает размер хранилища, вытеснение по времени использования.

- **Повторы запросов.** `withRetry` настраивается: `maxAttempts`, `baseDelayMs`, `maxDelayMs`, `jitterRatio`, `retryOnNetwork`, `retryOnTimeout`. Свои политики через `shouldRetry`, `computeDelay`, `onBeforeRetry`. `Retry-After` от сервера имеет приоритет над вычисленной задержкой.

- **Ошибки.** `ApiError` с геттерами `isRetryable`, `isCancelled`, `isAuthError`, `isUncertain` и другими. `err.fields` - готовая структура `Record<string, string>` для формы, если сервер отдаёт плоский формат. `err.rawBody` - оригинальное тело ответа для всего остального. Свой разбор через `parseErrorBody`.

- **Транспорт.** Валидация `baseUrl`, `timeoutMs`, `fetch` и порядка слоёв при создании клиента. Заголовки принимаются как `Record`, `Headers` или массив пар. `defaultHeaders` для сквозных заголовков. `timeoutMs` и `signal` в конкретном запросе. `requestWithMeta` возвращает HTTP-метаданные вместе с данными - для случаев, когда заголовок ответа влияет на дальнейшие действия: `Retry-After` в `202 Accepted`, `Location` в `201`, `X-Request-Id` для логов. `fetchOptions` для остальных параметров `fetch`.

  Асинхронные операции сервер может подтвердить ответом `202 Accepted` с заголовком `Retry-After`. Значение паузы в миллисекундах доступно в `meta.retryAfterMs` - ровно таким, каким его прислал сервер. Верхнюю границу библиотека не ставит: сколько ждать, решает приложение.

  ```ts
  const { meta } = await client.requestWithMeta({
    path: '/api/jobs',
    method: 'POST',
    body: { action: 'start' },
  });
  await new Promise((resolve) => setTimeout(resolve, meta.retryAfterMs ?? 1000));
  ```

- **Тела запросов.** JSON, `FormData`, `Blob`, `File`, `ArrayBuffer`, `TypedArray`, `DataView`, `URLSearchParams`, `ReadableStream`, Node.js `stream.Readable`. Работа с типами из iframe и Worker. Рекурсивная проверка: вложенные несериализуемые значения отклоняются до отправки с `BODY_SERIALIZATION_ERROR`.

- **Слои.** Свой слой - объект из четырёх полей: `name`, `stage`, `wrap`, `attach`. `LayerContext` даёт доступ к `warn`. Приоритеты `2.5` и `1.5` для вставки между встроенными.

## Установка и первый запрос

```
npm install fetch-layers
```

```ts
import { createClient } from 'fetch-layers';

const client = createClient({ baseUrl: '/api' });

const products = await client.get<Product[]>('/products');

const review = await client.post('/reviews', {
  productId: products[0].id,
  rating: 5,
  comment: 'Отличный товар',
});
```

Оба метода возвращают распарсенное тело ответа. `post` отправляет объект как JSON. Любая ошибка приходит как `ApiError` - её можно поймать через `try/catch` или `.catch()`.

### Подключение слоёв

Опция `layers` принимает массив слоёв в порядке от самого внешнего к самому внутреннему:

```ts
import { createClient } from 'fetch-layers';
import {
  withAuth,
  withRetry,
  withIdempotency,
  sessionStorageSource,
} from 'fetch-layers/layers';

const client = createClient({
  baseUrl: '/api',
  layers: [
    withIdempotency(sessionStorageSource()),
    withRetry({ maxAttempts: 3 }),
    withAuth({ provider: sessionProvider }),
  ],
});
```

Что делают слои в этом порядке:

- `withIdempotency` оборачивает всё остальное. Ключ генерируется один раз на операцию и не меняется при повторах.
- `withRetry` повторяет запрос при 5xx, сети и таймаутах, но не трогает ключ.
- `withAuth` добавляет заголовки авторизации и обновляет токен при 401.

Порядок нельзя переставить произвольно - библиотека проверяет его при создании клиента. Если поменять `withIdempotency` и `withRetry` местами, ключ будет генерироваться заново на каждом повторе - это ошибка. `createClient` выбросит исключение с указанием, какой слой нарушил правило.

Если слои не нужны, `createClient({ baseUrl: '/api' })` даёт чистый HTTP-клиент без авторизации, повторов и идемпотентности.

## Требования

Библиотека работает на Node.js 20.6+, в современных браузерах, Deno и Bun.

Нужен глобальный `fetch`. Если его нет, `createClient` выбросит исключение.

Пакет только ESM. CommonJS не поддерживается.

`crypto.randomUUID` нужен только если подключён `withIdempotency` со встроенным генератором ключей. Библиотека проверяет его при первом мутирующем запросе.

## Модули

Библиотека разбита на модули. Размер бандла зависит от того, что импортируете.

| Модуль                    | Что экспортирует                                                                                          |
| ------------------------- | --------------------------------------------------------------------------------------------------------- |
| `fetch-layers`             | `createClient`, `ApiError`, `toApiError`, `ErrorBodyParser`, хранилища и публичные типы                   |
| `fetch-layers/layers`      | Фабрики всех встроенных слоёв и источники ключей идемпотентности                                          |
| `fetch-layers/auth`        | Типы `SessionProvider`, `RefreshResult`, `SessionExpiredReason`, `resetRefreshCircuit`                    |
| `fetch-layers/idempotency` | `IdempotencySource`, `IdempotencyContext`, `IdempotencyOutcome`, `createSessionSource`, `stableSerialize` |
| `fetch-layers/retry`       | Только `withRetry` и его опции                                                                            |
| `fetch-layers/storage`     | `StorageLike`, `createMemoryStorage`, `fromWebStorage`                                                    |

### Прямые импорты для минимального размера

`fetch-layers/layers` реэкспортирует все три слоя. Если используете только один, импортируйте его напрямую: бандлер не потянет остальные.

```ts
import { withRetry } from 'fetch-layers/retry';
import { withAuth } from 'fetch-layers/auth';
import { withIdempotency, sessionStorageSource } from 'fetch-layers/idempotency';
```

`fetch-layers/layers` остаётся удобным вариантом для типового случая: один импорт вместо трёх.

## Как устроены слои

Каждый слой - обёртка вокруг функции запроса. Метод `wrap` получает `next` и возвращает свою версию. Здесь библиотека следует паттерну Decorator (GoF): добавляет поведение, сохраняя интерфейс. Первый слой в массиве получает запрос первым, последний - последним. Встроенные слои идут в порядке: идемпотентность, повторы, авторизация. Последним запрос получает транспорт.

У каждого слоя есть приоритет (stage). Чем больше число, тем раньше слой получает запрос. Встроенные приоритеты: `withIdempotency: 3`, `withRetry: 2`, `withAuth: 1`. Если нужен свой слой между встроенными, используйте дробные значения: `2.5` встанет между идемпотентностью и повторами, `1.5` - между повторами и авторизацией.

Слои без stage в проверке не участвуют. Их можно ставить в любое место массива.

Порядок слоёв не может быть произвольным. Ключ идемпотентности должен сгенерироваться до первой попытки, иначе каждый повтор создаст новый ключ и дедупликация сломается. Авторизация должна стоять после повторов, чтобы 401 попал в auth-слой, а не в retry. `createClient` проверяет порядок и выбрасывает исключение, если он нарушен: в сообщении будет имя слоя, который нарушает порядок.

У каждого клиента собственный экземпляр состояния. Один и тот же объект `Layer` можно передать в два `createClient`: у каждого будет свой `RefreshManager`, свой набор предупреждений, свой счётчик. Состояние одного клиента не влияет на другой.

### Почему выбрана слоистая архитектура вместо хуков или интерцепторов

Слой управляет вызовом: может вызвать `next` несколько раз, перехватить ошибку и вызвать снова с другими данными, выполнить код до и после. Колбэк так не может: он получает данные и возвращает их обратно, но не решает, когда и сколько раз вызвать следующий шаг.

Хук в ky или ofetch, интерцептор в axios - это колбэки, которые вызываются в фиксированной точке: до запроса или после ответа. Каждый получает данные и возвращает их.

`withRetry` вызывает `next` в цикле, пока не получит успешный ответ. `withAuth` перехватывает 401, отдельно делает refresh, затем вызывает `next` с новым токеном. `withIdempotency` оборачивает вызов целиком и удаляет ключ только после подтверждения от сервера.

Хуки и интерцепторы умеют только менять данные на входе и выходе. Логику цикла и порядка они не описывают.

## Совместная работа с TanStack Query

fetch-layers встраивается в `queryFn` и `mutationFn`.

```tsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

const client = createClient({
  baseUrl: '/api',
  layers: [
    withIdempotency(sessionStorageSource()),
    withAuth({ provider: sessionProvider }),
  ],
});

function useUser(id: string) {
  return useQuery({
    queryKey: ['user', id],
    queryFn: ({ signal }) => client.get<User>(`/users/${id}`, { signal }),
  });
}

function useCreateOrder() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: (order: Order) => client.post<Order>('/orders', order),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ['orders'] });
    },
  });
}
```

`queryFn` получает `signal` от TanStack Query, fetch-layers его принимает и объединяет с внутренним таймаутом. Отмена работает в обе стороны.

Основной конфликт - retry. У TanStack Query есть свой retry для `useQuery`, у fetch-layers - свой для HTTP. Если оба включены, 3 попытки x 3 попытки = 9 запросов. Оставьте retry в одном месте:

```ts
// Retry в fetch-layers, TanStack Query без retry.
const client = createClient({
  baseUrl: '/api',
  layers: [withRetry({ maxAttempts: 3 })],
});

useQuery({
  queryKey: ['user', id],
  queryFn: () => client.get<User>(`/users/${id}`),
  retry: false,
});
```

Остальное работает без адаптеров: `ApiError` пробрасывается в `error`, `signal` принимается как есть, DevTools показывает вызовы `queryFn` без изменений.
